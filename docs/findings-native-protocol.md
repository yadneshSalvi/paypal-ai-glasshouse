## Privacy, denial and recovery

- Invite a separate browser capability through the normal workspace UI as a viewer. The viewer can read only explicitly shared finding versions; private proposals, later private revisions and other users' encrypted conversations remain unavailable. Support/challenge/revise/share controls must be absent or disabled. A guessed private version/export is denied by the server.
- With a writing peer, challenge one shared current version. Verify the peer can recover its exact submitted decision after a lost response without gaining general access to the new private revision. Its permitted library still shows the last shared version until the creator shares another.
- In a normal second workspace/tab, switch context, revoke a member, lower a role and archive/restore a quiescent Sample room. Stale responses must not disclose a previous room; mutations must reflect current authority. Restoring a room preserves its finding/report history. Original session expiry is never extended.
- Temporarily interrupt a read using the browser's normal network controls. Verify a meaningful error and **Retry current read**. Interrupt a review response after submission, restore the network and use **Recover original decision**. Reload while that request is unresolved. Recovery must reuse its exact request ID/content/current-version precondition and produce one saved revision. Do not simulate this by editing application state or weakening server checks.
- Test a stale concurrent review in two tabs. The losing action must preserve the newer version and show a useful conflict/recovery path. Refreshing a read must not silently submit a new decision. Encryption/configuration failures must preserve stored records and deny disclosure.
